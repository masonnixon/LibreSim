## Executive summary

LibreSim's block library and API layer are extensive and well-tested at the behavioral level, but the audit found **two correctness defects in the numerical heart of the product** — the OSK integrator: the RK4 stepper applies a wrong coefficient on its second stage (making the "4th-order" solver not 4th order), and intermediate integration passes never advance simulation time (degrading every multi-stage method for time-driven systems). Because these errors still produce *convergent, plausible-looking* trajectories, and the test suite has no convergence-order assertions, they are invisible to both eyeballing and the current tests. A third structural issue — kernel state living in class attributes — makes concurrent simulations in the one FastAPI process corrupt each other.

## Critical findings

### 1. RK4 second stage uses h/4 instead of h/2
`backend/src/osk/state.py:119-139` (`_propagate_rk4`) + `:165-191` (`updateclock`)

Trace of one full step (h = `dtp`):

| pass | `State.dt` entering pass | propagate computes | classical RK4 wants |
|------|--------------------------|--------------------|---------------------|
| 0 (k1) | `h` (from `reset`) | `x0 + (dt/2)·k1 = x0 + h/2·k1` ✓ | `x0 + h/2·k1` |
| 1 (k2) | `h/2` (set by `updateclock` after pass 0) | `x0 + (dt/2)·k2 = x0 + **h/4**·k2` ✗ | `x0 + h/2·k2` |
| 2 (k3) | `h` | `x0 + h·k3` ✓ | `x0 + h·k3` |
| 3 (k4) | `h` | `x0 + h/6(k1+2k2+2k3+k4)` ✓ | same |

The bug is a double-halving: `_propagate_rk4` hardcodes `dt/2` for passes 0–1, **and** `updateclock` also halves `State.dt` for `kpass in [0,1]` (`:184-186`). Note the Merson branch does it right — `updateclock` keeps `dt = dtp` and `_propagate_merson` carries all fractions explicitly. RK2 also happens to be consistent. Only RK4 mixes the two conventions.

Effect: k3 is evaluated at the wrong point, so the method loses its 4th-order error cancellation — it silently degrades to ~2nd order accuracy while carrying 4 function evaluations per step. Every RK4 simulation result in the app is affected (RK4 is the default method, `state.py:25`).

**Fix**: delete the RK4 `dt` juggling in `updateclock` (make it like Merson's branch: `dt = dtp` always). **Then add the missing test**: integrate `x' = -x` (and a driven `x' = sin(t)` case) over a fixed interval at h and h/2 and assert the error ratio ≈ 16 (4th order). `tests/test_osk.py` currently has no accuracy/convergence assertion at all, which is why this survived.

### 2. Intermediate passes never advance simulation time
`state.py:165-191` — `State.t` only advances by `dtp` when a step completes; it is never set to `t + h/2` / `t + h` for the middle stages.

Every source block computes its output from `State.t` (e.g., Sine, Step, Clock, `TransportDelay` at `continuous.py:582`). So during an RK4 step, k2/k3/k4 are all evaluated with the **step-start time**: for any non-autonomous system (driven by time-varying inputs — most control models), all multi-pass methods collapse toward 1st-order accuracy in the drive terms, independent of finding #1. The classical OSK design advances a pass-local time; this port dropped it. Fix: have `updateclock` set `State.t = State.t1 + <stage offset>` per pass (0, h/2, h/2, h for RK4; 0, h/3, h/3, h/2, h for Merson), restoring `t1 + dtp` on completion.

### 3. Kernel state is process-global — concurrent simulations corrupt each other
`state.py:18-29` (class attrs `t`, `dt`, `kpass`, `ready`, `method`) and `sim.py:40-62` (`Sim.__init__` assigns to **class** attributes).

`SimulationRunner` is async and yields (`runner.py:337,356`) mid-run, and simulations are launched via FastAPI `BackgroundTasks` — so two users (or one user restarting a sim) genuinely interleave two runs in one process, each scribbling over the same `State.t`, `State.kpass`, and `Sim.clock`. Symptoms would be sporadic: time jumping, stop flags crossing between sessions, method switching mid-run. Even single-user: constructing a second `Sim` invalidates a running one.

This is faithful to the original C++ OSK's static design, but that assumed one simulation per process. Options in ascending effort: (a) a module-level `asyncio.Lock`/semaphore serializing runs (cheap, honest), (b) move timing into an instance-level `SimContext` passed to blocks, (c) run each simulation in a subprocess. Given step-mode and pause features, (b) is the right destination; (a) is the safe interim.

## Medium findings

4. **Results keyed by `id(obj)`** — `sim.py:135-138`: `id()` values are reused after garbage collection, and the adapter must maintain a parallel id→block map; a stale mapping across re-runs silently mixes signals. Give blocks a stable `block_id` (the adapter already knows model node ids).
5. **`sample()` periodic branch is a no-op** — `state.py:78-80`: for non-event sampling it unconditionally sets `ready = 1`, so per-stage sample intervals (`sdt`) are ignored. Either implement periodic sampling or remove the parameter — right now it looks configurable but isn't.
6. **Codegen semantic drift risk** — four parallel reimplementations of every block's semantics (`codegen/languages/{python,c,cpp,rust}/blocks/*`, ~1k lines each for aerospace alone). You already have `codegen_verification/` fixtures and `test_codegen_accuracy.py` — extend that into a matrix test (every example × every language × compare against OSK within tolerance) in CI, because any fix from findings #1/#2 must land in five places (OSK + 4 generators) or the generated code will disagree with the simulator. **Check whether the four generators replicated the RK4 h/4 bug** — if they implement classical RK4 correctly, generated code already disagrees with the app today.
7. **Unbounded in-memory results** — `sim.py:128-138` appends every block's output every report tick; a long sim with many scopes grows without limit (the runner's `_max_history_size` bounds *step history*, not results). Consider decimation or streaming to the frontend.
8. **156 committed zip archives** — `codegen_verification/*.zip` dominates the repo's object count (156 of 466 tracked files). Generate them in CI instead of tracking them, or move to Git LFS; repo clones and diffs pay for this forever.

## Minor / hygiene

9. `Sim.vObj` is dead ("kept for compatibility") and `Sim`'s mutable class-attribute defaults (`dts: list = []`) are the classic shared-default trap — instance attributes after fixing #3.
10. Working tree is dirty (`docker-compose.yml`, `frontend/vite.config.ts` modified) on branch `uimods` — commit or stash so audits/builds are reproducible.
11. `.claude/` context: repo has no CLAUDE.md; given the cross-repo dependency (orbitlink_cubesat's validation scripts import `backend/src` from here), documenting the public adapter surface (`MDLParser`, `ModelCompiler`, `OSKAdapter`, `SimulationConfig`) and a stable import path contract would prevent the path breakage found in the cubesat repo's audit.

## What's notably good

- Block library breadth (20 categories incl. sensor fusion, RF, navigation) with per-domain test files.
- `test_crosstalk_bug.py` — keeping a named regression test for a past bug is exactly the right pattern; findings #1/#2 deserve the same treatment.
- The codegen verification fixture set (idea) — it just needs to run in CI rather than live as artifacts.

## Suggested priority order

1. Fix RK4 coefficient (#1) — one-line change + convergence-order test.
2. Advance pass-local time (#2) — small change, big correctness win for driven models.
3. Serialize or isolate concurrent runs (#3a now, #3b later).
4. Codegen×OSK matrix test (#6) so all five implementations stay in lockstep.
